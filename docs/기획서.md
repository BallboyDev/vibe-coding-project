# iPad Markdown Editor 개발 기획서
> 프로젝트명: `아이패드 TXT Editor`

## 1. 문서 개요

### 1.1 프로젝트 정의
본 프로젝트는 Apple iPad에서 구동되는 텍스트 기반 파일 편집 애플리케이션을 개발하는 프로젝트이다.  
앱의 핵심 목적은 iPad에서 로컬 텍스트 파일과 디렉토리를 손쉽게 탐색하고, 마크다운 중심의 문서를 안정적으로 편집 및 저장할 수 있는 환경을 제공하는 것이다.

### 1.2 문서 목적
이 문서는 다음 목적을 가진다.

1. 제품의 목표와 MVP 범위를 명확히 정의한다.
2. 화면 구조, 주요 사용자 흐름, 기능 요구사항을 구체화한다.
3. 구현 시 필요한 기술 방향과 예외 처리 기준을 정리한다.
4. Codex 또는 기타 AI Agent가 일관된 기준으로 개발을 진행할 수 있도록 한다.

### 1.3 프로젝트 목표
1. iPad 환경에서 동작하는 파일 기반 텍스트 에디터 앱을 개발한다.
2. 앱 내부 `Documents` 디렉토리를 기준으로 파일 및 디렉토리 탐색 기능을 제공한다.
3. 텍스트 파일과 마크다운 파일의 생성, 수정, 삭제, 이름 변경 기능을 제공한다.
4. 마크다운 파일에 대해 기본적인 문법 하이라이팅을 제공한다.
5. 키보드 중심 사용자를 위해 `Cmd + S` 저장 단축키를 지원한다.

### 1.4 비목표
초기 버전에서는 아래 항목을 구현 범위에서 제외한다.

1. 실시간 협업 기능
2. Git 동기화 기능
3. 복수 탭 편집 기능
4. 외부 클라우드 저장소 직접 연동
5. 완성도 높은 WYSIWYG 마크다운 편집

## 2. 개발 원칙

### 2.1 개발 방식
1. 초기 Xcode 프로젝트 생성 이후의 설계, 구현, 구조화는 AI Agent 중심으로 진행한다.
2. 명시되지 않은 세부 구현은 본 기획서의 방향성을 해치지 않는 범위에서 자율적으로 결정한다.
3. 기능 구현 시 확장성과 유지보수성을 우선한다.

### 2.2 개발 환경
1. 개발 툴: `Xcode`
2. 대상 플랫폼: `iPadOS`
3. 언어: `Swift`
4. UI 프레임워크: `SwiftUI` 우선
5. 필요 시 텍스트 편집 고도화를 위해 `UIKit` 브리징을 허용한다.

### 2.3 품질 원칙
1. 저장 안정성을 UI 화려함보다 우선한다.
2. 파일 시스템 관련 기능은 실패 가능성을 전제로 예외 처리를 포함한다.
3. 동일한 기능 로직은 재사용 가능한 단위로 분리한다.
4. MVP 단계에서는 구현 복잡도가 높은 기능보다 핵심 편집 흐름 완성을 우선한다.

## 3. 대상 사용자와 사용 시나리오

### 3.1 대상 사용자
1. iPad에서 메모, 문서, 마크다운 파일을 직접 관리하려는 사용자
2. 키보드 연결 상태에서 간단한 문서 편집을 자주 수행하는 사용자
3. VSCode와 유사한 탐색 구조에 익숙한 사용자

### 3.2 핵심 사용 시나리오
1. 사용자는 앱 실행 후 좌측 탐색기에서 폴더와 파일을 탐색한다.
2. 사용자는 새 마크다운 파일 또는 텍스트 파일을 생성한다.
3. 사용자는 파일을 선택하여 내용을 편집한다.
4. 편집 내용은 즉시 원본 파일에 반영되지 않고, 명시적 저장 시점에만 반영된다.
5. 사용자는 컨텍스트 메뉴 또는 `Cmd + S`를 통해 저장한다.

## 4. 기능 범위

### 4.1 MVP 기능
초기 버전에서 반드시 포함해야 하는 기능은 아래와 같다.

1. 디렉토리 트리 탐색
2. 파일 열기
3. 텍스트 편집
4. 파일 저장
5. 파일 및 디렉토리 생성
6. 파일 및 디렉토리 이름 변경
7. 파일 및 디렉토리 삭제
8. 마크다운 기본 하이라이팅
9. 상태 표시줄 정보 노출
10. 컨텍스트 메뉴 및 키보드 단축키 지원

### 4.2 후순위 기능
아래 기능은 구조를 고려하되 MVP에서는 필수로 구현하지 않는다.

1. 마크다운 HTML 미리보기
2. 자동 저장 옵션
3. 최근 연 파일 목록
4. 복수 파일 동시 편집
5. 깨진 파일 복구 기능

## 5. 앱 구조 설계

### 5.1 전체 레이아웃
앱은 VSCode와 유사한 3단 구성을 기본 방향으로 한다.

1. 좌측: 파일/디렉토리 트리 네비게이션 영역
2. 상단: 현재 파일 정보 표시 영역
3. 중앙: 텍스트 편집 영역
4. 하단: 상태 정보 표시 영역

### 5.2 네비게이션 영역
1. 루트 경로는 앱 샌드박스 내부의 `Documents` 디렉토리로 고정한다.
2. 디렉토리 구조는 트리 형태로 표시한다.
3. 디렉토리는 확장/축소가 가능해야 한다.
4. 파일 선택 시 해당 파일을 에디터에 로드한다.
5. 정렬 기준은 기본적으로 다음 순서를 따른다.
   - 디렉토리 우선
   - 이름 오름차순
6. 숨김 파일은 초기 버전에서 표시하지 않는다.

### 5.3 파일 정보 영역
상단 파일 정보 영역에는 아래 정보를 표시한다.

1. 현재 열린 파일명
2. 파일 확장자
3. 수정 여부
4. 저장 상태

수정 여부 표시는 사용자가 즉시 인지할 수 있어야 하며, 파일명 옆 `*` 또는 별도 텍스트로 표현한다.

### 5.4 에디터 영역
1. 선택한 파일의 텍스트 내용을 표시한다.
2. 사용자가 텍스트를 자유롭게 입력, 수정, 삭제할 수 있어야 한다.
3. 편집 중인 내용은 메모리상의 임시 상태로 유지한다.
4. 저장 전까지 원본 파일은 변경하지 않는다.
5. 파일이 선택되지 않은 경우 안내용 빈 상태 화면을 표시한다.

### 5.5 상태 정보 영역
MVP에서 우선 제공할 정보는 아래와 같다.

1. 파일 확장자
2. 파일 크기
3. 저장 상태

추가 가능 항목은 아래와 같다.

1. 커서 위치
2. 선택된 문자 수
3. 줄 수
4. 인코딩 정보

초기 단계에서는 구현 난도가 낮고 안정적으로 제공 가능한 정보만 우선 노출한다.

## 6. 상세 기능 요구사항

### 6.1 파일 및 디렉토리 생성
1. 디렉토리 보조 클릭 또는 길게 터치 시 컨텍스트 메뉴를 표시한다.
2. 디렉토리 컨텍스트 메뉴에는 아래 항목을 표시한다.
   - `디렉토리 생성`
   - `파일 생성`
   - `이름 변경`
   - `삭제`
3. 새 파일 생성 시 기본 파일명 입력 UI를 제공한다.
4. 파일 생성 시 확장자는 사용자가 직접 입력할 수 있도록 한다.
5. 이름이 비어 있거나 이미 존재하면 생성하지 않고 오류 메시지를 표시한다.

### 6.2 파일 및 디렉토리 이름 변경
1. 파일과 디렉토리 모두 이름 변경을 지원한다.
2. 이름 변경 시 기존 경로와 동일한 위치에서 이름만 수정한다.
3. 중복 이름이 존재하면 변경을 막고 사용자에게 알린다.
4. 이름 변경 후 트리 목록과 현재 선택 상태를 즉시 갱신한다.

### 6.3 파일 및 디렉토리 삭제
1. 파일과 디렉토리 모두 삭제를 지원한다.
2. 삭제 전 확인 다이얼로그를 표시한다.
3. 디렉토리 삭제 시 하위 파일 및 폴더가 함께 삭제된다는 점을 명시한다.
4. 현재 열려 있는 파일이 삭제될 경우 에디터는 빈 상태로 전환한다.

### 6.4 파일 열기
1. 파일 선택 시 에디터 영역에 내용을 로드한다.
2. 텍스트로 읽을 수 없는 파일은 열지 않고 오류 메시지를 표시한다.
3. 매우 큰 파일은 초기 버전에서 비권장 대상으로 간주하며, 필요 시 로드 제한 메시지를 표시할 수 있다.

### 6.5 파일 편집
1. 열린 파일은 자유롭게 편집 가능해야 한다.
2. 편집이 발생하면 즉시 `수정됨` 상태로 전환한다.
3. 수정된 내용은 저장 전까지 디스크에 반영하지 않는다.
4. 다른 파일을 선택하려 할 때 현재 파일에 미저장 변경사항이 있으면 아래 중 하나를 수행한다.
   - 저장 후 이동
   - 저장하지 않고 이동
   - 취소

### 6.6 저장 정책
1. 저장은 사용자가 명시적으로 실행했을 때만 수행한다.
2. 저장 트리거는 아래 두 가지를 우선 지원한다.
   - `Cmd + S`
   - 컨텍스트 메뉴의 `저장`
3. 저장 성공 시 수정 상태를 해제한다.
4. 저장 실패 시 기존 편집 내용은 메모리에 유지하고 오류 메시지를 표시한다.
5. 미저장 상태의 파일은 트리와 상단 정보 영역에서 식별 가능해야 한다.

### 6.7 마크다운 하이라이팅
1. 대상 확장자는 우선 `md`, `markdown`으로 한정한다.
2. 기본 하이라이팅 대상은 아래 문법으로 한다.
   - 제목
   - 리스트
   - 체크리스트
   - 인라인 코드
   - 코드 블록
   - 링크
   - 굵게/기울임
   - 인용문
3. 오픈소스 Swift 라이브러리 사용을 허용한다.
4. 라이브러리 선정 기준은 아래와 같다.
   - 유지보수 상태가 양호할 것
   - iPadOS 적용이 가능할 것
   - Swift 기반 프로젝트와 통합이 쉬울 것
5. 초기 버전에서는 미리보기 렌더링이 아닌 편집기 내 강조 표시를 목표로 한다.

### 6.8 컨텍스트 메뉴
1. 파일과 디렉토리의 컨텍스트 메뉴 항목은 대상 종류에 따라 다르게 노출한다.
2. 파일 컨텍스트 메뉴에는 아래 항목을 표시한다.
   - `이름 변경`
   - `삭제`
   - `저장` (미저장 상태일 때만)
3. 디렉토리 컨텍스트 메뉴에는 아래 항목을 표시한다.
   - `디렉토리 생성`
   - `파일 생성`
   - `이름 변경`
   - `삭제`

### 6.9 키보드 단축키
초기 버전에서 아래 단축키를 지원한다.

1. `Cmd + S`: 현재 파일 저장

추후 확장 가능한 단축키 예시는 아래와 같다.

1. `Cmd + N`: 새 파일 생성
2. `Cmd + Shift + N`: 새 디렉토리 생성

## 7. 상태 및 예외 처리 정책

### 7.1 미저장 데이터 보호
1. 사용자가 편집 중인 파일에서 벗어나려 할 때 미저장 변경사항 여부를 반드시 확인한다.
2. 앱이 백그라운드로 전환되는 경우에도 메모리 상태는 유지하도록 설계한다.
3. 초기 버전에서는 자동 저장을 기본 비활성 정책으로 둔다.

### 7.2 오류 처리
아래 상황에서는 사용자에게 명확한 오류 메시지를 제공한다.

1. 파일 읽기 실패
2. 파일 저장 실패
3. 이름 충돌
4. 권한 문제
5. 삭제 실패
6. 지원하지 않는 파일 형식

오류 메시지는 가능한 한 원인을 단문으로 설명하고, 사용자가 다음 행동을 판단할 수 있게 구성한다.

### 7.3 빈 상태 처리
1. 선택된 파일이 없을 때는 안내 문구를 표시한다.
2. 파일이 하나도 없을 경우 새 파일 생성 유도 문구를 표시한다.

## 8. UI/UX 방향

### 8.1 테마
1. 기본 테마는 다크 테마로 한다.
2. 색상 방향은 VSCode 또는 iPad 다크 계열 UI에 가까운 차분한 톤을 사용한다.
3. 구체적인 색상값은 구현 단계에서 자율 선정하되, 가독성을 우선한다.

### 8.2 디자인 원칙
1. 시각적 화려함보다 편집 집중도를 우선한다.
2. 탐색기, 에디터, 상태 정보가 명확히 구분되어야 한다.
3. 터치 환경과 키보드 환경 모두에서 사용 가능해야 한다.
4. 작은 화면에서도 레이아웃이 무너지지 않아야 한다.

### 8.3 상호작용 원칙
1. 길게 터치와 보조 클릭 모두 지원 가능한 구조를 우선 고려한다.
2. 사용자가 현재 선택한 파일, 수정 상태, 저장 상태를 쉽게 파악할 수 있어야 한다.
3. 파괴적 동작에는 반드시 확인 절차를 둔다.

## 9. 기술 설계 방향

### 9.1 아키텍처 방향
아래 원칙을 따른다.

1. UI 레이어와 파일 처리 로직을 분리한다.
2. 파일 시스템 접근 로직은 별도 서비스 단위로 분리한다.
3. 상태 관리는 화면 단위와 기능 단위로 구분한다.
4. 마크다운 하이라이팅 로직은 편집기 로직과 분리 가능하도록 구성한다.

### 9.2 권장 모듈 구성
예상 구조는 아래와 같다.

1. 앱 진입 및 공통 설정
2. 파일 탐색 기능
3. 파일 편집 기능
4. 파일 저장 및 변경 상태 관리
5. 마크다운 하이라이팅 기능
6. 공통 UI 컴포넌트
7. 디자인 시스템 또는 테마 정의

## 10. 프로젝트 구조 원칙

프로젝트 구조는 아래 규칙을 따른다.

1. 디자인 관련 코드와 기능 구현 코드를 분리한다.
2. 기능은 도메인 기준으로 분리하며, 하나의 파일에 과도하게 집중시키지 않는다.
3. 동일한 기능을 여러 화면에서 사용할 가능성이 있으면 공통 모듈로 분리한다.
4. 파일 시스템, 편집 상태, UI 상태를 혼합하지 않는다.
5. 재사용성과 테스트 용이성을 고려한 구조를 우선한다.

## 11. 개발 우선순위

### 11.1 1차 개발 단계
1. 기본 앱 레이아웃 구성
2. `Documents` 디렉토리 로딩
3. 파일 트리 표시
4. 파일 열기 및 내용 표시
5. 텍스트 편집
6. 명시적 저장 기능

### 11.2 2차 개발 단계
1. 파일/디렉토리 생성
2. 이름 변경
3. 삭제
4. 미저장 상태 경고 처리
5. 상태 정보 바 구성

### 11.3 3차 개발 단계
1. 마크다운 하이라이팅 도입
2. 키보드 단축키 강화
3. UI 디테일 보완
4. 예외 처리 메시지 정리

## 12. 완료 기준

아래 항목이 모두 충족되면 MVP 완료로 간주한다.

1. 사용자가 앱 내부 `Documents` 기준으로 파일과 폴더를 탐색할 수 있다.
2. 사용자가 파일을 생성, 수정, 저장, 삭제, 이름 변경할 수 있다.
3. 사용자가 디렉토리를 생성, 삭제, 이름 변경할 수 있다.
4. 마크다운 파일에서 기본 문법 하이라이팅이 동작한다.
5. 미저장 상태가 UI에 반영되고 저장 시 해제된다.
6. 주요 실패 상황에서 앱이 종료되지 않고 오류를 안내한다.
